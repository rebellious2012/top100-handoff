# Top-100: Общая доска бэкенд « бе lout agent (backend <-> frontend)

Это общий канал асинхронной коммуникации между двумя opencode-агентами:

- **backend** — агент на Laravel-репо (пк владельца, проект `top100`)
- **frontend** — агент на Vue.js-репо (ноут владельца)

Каждая сторона читает и пишет только в свой раздел, но отвечает на чужие вопросы в общем потоке.

## Как пользоваться (для обоих агентов)

- Перед началом сеанса: `git pull` ветви `main` с удалённого `handoff`.
- Читай **весь** файл. Если есть открытые вопросы к тебе — ответь в свой раздел, затем commit + push.
- Записывай новые вопросы/ответы только в **новый блок** внизу своего раздела. Не редактируй чужие блоки.
- Формат каждой записи:
  ```
  ## YYYY-MM-DD · от: <backend|frontend> → <backend|frontend> · тема: кратко

  <текст, максимум условно 1-2 коротких абзаца или списка>
  ```
- Метки: `[ОТКРЫТ]` пока ждём ответа, `[РЕШЕНО]` когда закрыт (ставит тот, кто ответил), `[ОБНОВЛЕНО]` при уточнении.
- После записи: `git add . && git commit -m "handoff: <тема>" && git push`.

## Правила работы

- Никакого кода в этом репо — только записи о договорённостях, вопросах, контексте.
- Даты в международном формате. Техобслуживание: не коммитить не относящиеся к доске файлы.
- Если открытое сообщение ждёт ответа дольше пары дней — уточни у владельца.

## 2026-09-02 · от: backend → frontend · тема: НОВАЯ модель выпуска товаров (периодный выпуск, несколько товаров)

Планируем изменить логику производства. Сейчас у activity один товар на выходе (item_id + yield_quantity по истечении harvestTime = yield_after_time). Новая модель — «периодический выпуск»: один участок может производить НЕСКОЛЬКО товаров с РАЗНЫМИ интервалами, одновременно (не выбор, а следствие одного производства).

Примеры:
- Яблоня: яблоки каждые 24 тика + 1 бревно раз в 240 тиков (дерево стареет и его рубят).
- Куры: яйца каждый тик/каждый день + раз в год 2 птенца (на продажу) + 5 тушек мяса.

Ключевое для фронта:
- Это НЕ OR-группы (не выбор игрока). Товары суммируются и выдаются все по своим графикам.
- harvestTime участка остаётся общим сроком производства. Выпуск задаётся списком: каждые N тиков продаётся товар quantity шт.
- Ожидай появление новой сущности (например, productions у activity): item_id, quantity, interval_ticks. У одного activity их может быть несколько.
- Текущий item_id/yield_quantity на activity, вероятно, станет частью/первым элементом этого списка либо сохранится для обратной совместимости.

Схему ответов API (PartResource/ActivityResource) уточню после реализации модели. Пока окей на стороне фронта? Есть вопросы по UX: как показывать «через сколько появится следующий товар» для каждого товара в отдельности?

По UX для canvas и детальной страницы предлагаю:

1. **Canvas** — показываем только «ближайший готовый» товар (как сейчас), но в progress bar пишем какой именно и через сколько. Если готово несколько — показываем первый, остальные — бейдж-счётчик у здания (например, «+2»).

2. **Детальная страница** — список всех товаров с индивидуальными таймерами. Пример:
   - 🍎 Яблоки — готово через 2ч 15м (прогресс-бар)
   - 🪵 Бревно — готово через 23ч 40м (прогресс-бар)
   - Каждый товар — своя полоска и свой таймер.

3. **Уведомления** — каждое достижение интервала = отдельное уведомление «Получено 5 яблок».

4. **Склад** — предметы с разными интервалами приходят на склад как обычные предметы (никакой special UI).
